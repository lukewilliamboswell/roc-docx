= Contribute to roc-docx

This chapter is for anyone changing the repository. Read the
xref:architecture.adoc#architecture[architecture] first: it is the enduring
design, and a change that conflicts with it changes the design in the same
pull request or does not land.

== Set up

Install `blueprint` as the
https://lukewilliamboswell.github.io/roc-blueprint/getting-started.html[roc-blueprint guide]
describes and put the latest Roc nightly on your `PATH` as `roc`. The machine
also needs `python3` and `xmllint` (libxml2) for the schema oracle. Blueprint
fetches everything else by digest: the repository's fixed tooling compiler,
pandoc and the shared release utility. LibreOffice is needed only for the
LibreOffice lane and is found through `SOFFICE`, `PATH` or the macOS
application bundle.

== Check a published release on the nightly

The daily `Nightly compatibility` workflow calls roc-automation's shared
published-release workflow on Ubuntu. It selects the latest final release
and the latest Roc nightly, then checks, builds and runs the examples in
that release's immutable archive. The report job maintains one issue when
those examples fail; the test jobs have read-only repository access.

Run it manually from the default branch with both selectors empty to test
the current pair. Set `nightly-tag` or `release-tag` to investigate a historical
pair; an override run leaves the current pair's tracking issue unchanged.
The shared workflow selects final releases, so a repository with only
prereleases has no compatibility result until its first final release.

The
https://lukewilliamboswell.github.io/roc-automation/downstream-status/[downstream dashboard]
links the run evidence and reports both release compatibility and the
repository's direct roc-automation pins. A green compatibility badge requires
a complete, recent pass; a green automation badge requires every pin to match
the dashboard's observed roc-automation main revision.

== Run the checks

[source,sh]
----
blueprint run check      # everything a pull request must pass
blueprint tasks          # each check on its own, and the fixture and release tasks
----

`check` runs these in order and reports every failure, not just the first:

[cols="1,3",options="header"]
|===
| Check | What it establishes

| oracle-provision
| The ECMA-376 schemas and their imports match the digests in `conformance/ledger.json`

| fmt, fmt-scripts
| Every Roc source is formatted; `roc fmt` is final

| lint
| The mechanical checks below hold

| scripts-test
| The lint rules' own `expect`s pass

| test
| Every `expect` reachable from `package/main.roc` passes

| cases
| Every data-driven case under `tests/` reports what its expectation records: each fixture passes through, and the package's snapshot of it is the one in `tests/snapshots/`

| manual
| Every Roc listing in this manual compiles and runs, as `tests/manual.roc`

| examples
| Every example prints what `tests/spec.json` records

| fuzz-smoke
| Every fuzz target builds, its declared examples and ceilings pass, and a one-second exploration finds nothing; targets build concurrently and report in order

| fixtures-check
| Committed pandoc fixtures match regeneration and every fixture has provenance

| oracle-schema
| Every XML part of every fixture validates against the schemas

| oracle-schema-written
| Every XML part of every document the cases wrote validates against the schemas

| oracle-snapshot
| pandoc's and the package's snapshots of every fixture conform to the snapshot contract and agree; it reads the package's snapshots that `cases` wrote
|===

The LibreOffice lane is a task of its own, because `check` does not need
LibreOffice:

[source,sh]
----
blueprint run libreoffice   # pandoc, LibreOffice and the package agree; LibreOffice reads each written document as its original
----

It runs the cases first, so it needs `roc` as well, and then compares
LibreOffice's snapshot of each document they wrote with its snapshot of the
fixture it came from, and LibreOffice's snapshot of each generated document
and each reviewed fixture with the package's:

[source,sh]
----
python3 -I oracle/compare_snapshots.py --written libreoffice tests/fixtures .roc-docx/passthrough
python3 -I oracle/compare_snapshots.py --lane libreoffice,package .roc-docx/generated
python3 -I oracle/compare_snapshots.py --lane libreoffice,package .roc-docx/review
python3 -I oracle/compare_snapshots.py --lane libreoffice,package .roc-docx/redline
----

Each comparison prints the LibreOffice version it ran. Pull-request CI runs
the lane with Ubuntu 24.04's `libreoffice-writer` package, LibreOffice 24.2,
and its fonts alone; a contributor's machine usually has a newer LibreOffice.
The lane passes on both, and where they read a document differently the
adapter reads what each writes or the difference is an accepted deviation
naming the version, so reproduce a CI-only finding in an `ubuntu:24.04`
container with that package rather than on your own machine.

Pull-request CI runs `check`, the LibreOffice lane and the manual build, and
nothing heavier. Sustained fuzz campaigns and benchmarks are not part of CI;
if they are wanted later they will be separate scheduled work.

== Write Roc the way this repository does

Follow the
https://gist.github.com/lukewilliamboswell/241a4e8adb7c89c7e0e02f1d303a8fa1[Roc style guide].
The rules that come up most here:

- A module's type block is its public surface: `Opc :: [].{ ... }` holds the
  API, private helpers sit below it, and every top-level `expect` has a `##`
  doc comment that names it.
- Configuration is a props record of defaulted fields passed beside the
  subject, as `Opc.open(bytes, {})` shows. A new option is a new defaulted
  field.
- Closed sets are tag unions. Fallible functions return `Try` with structured
  tags whose payloads carry the facts; let error unions merge through `?`
  instead of renaming tags, and use infix `?` to add context.
- Nothing under `package/` may `crash`: a document is untrusted input, and
  every failure is a named error.
- Keep accumulators uniquely owned so Roc updates them in place. The fuzz
  targets' allocation ceilings tell you when you have not.

== Mechanical checks

Where a rule can be checked by a program it is, because a check is more
reliable than guidance. `blueprint run lint` runs `scripts/lint.roc`, whose
rules are pure functions with their own `expect`s in `scripts/src/Lint.roc`.
It reports `path:line: message` for each violation. When a rule fires, fix the
source; when a rule is wrong, change the rule in the same pull request with
the reason. The rules are listed in the
xref:architecture.adoc#mechanical-checks[architecture].

== Data-driven cases

`tests/main.roc` is one program that runs every data-driven case, printing
each case's result and time and a summary of passes, updates, failures and
skips. A case's expectation is a committed text file, so a change in what the
package produces shows up as a diff to review:

[source,sh]
----
blueprint run cases          # every case against its expectation
blueprint run cases-update   # rewrite the expectations, then review the diff
----

The pass-through cases parse every fixture with `Docx.parse`, write it with
`Docx.to_bytes`, and require that the written document parses to one
`Docx.equivalent` to the original with nothing left to drop, and that
writing it twice, or writing what was written, gives the same bytes. Each
expectation under `tests/passthrough/` records what reading dropped, the
written package's size and FNV-1a digest, and its parts with their sizes and
content types, so the same digest on every host shows the output is
deterministic. The written documents go to `.roc-docx/passthrough/`, where
`oracle-schema-written` and the LibreOffice lane read them.

The generated cases build documents from the model in `tests/main.roc`, for
content no fixture holds together, such as one of every kind of tracked
change, and the documents of the `letter`, `agreement`, `minutes` and
`report` examples, built step for step as each example builds its own, so
that the documents the oracles read are byte for byte the examples'
outputs; a change to an example is made in its case too. Each must read
back as the model it was built from and then pass through as a fixture
does; its expectation under `tests/generated/` is the pass-through report
with what it reads back, such as its text, comments and tracked changes. The written
documents go to `.roc-docx/generated/`, which `oracle-schema-written`
validates and the LibreOffice lane compares with the package's snapshots.

The review cases edit every fixture as the `review_contract` example edits
its contract: a comment on the first line of text, a reply to the comment
that comes first, that thread resolved and the last of the fixture's own
comments removed when it has more than one. The edits must leave the text
as it was, and the edited document must write twice to the same bytes and
read back as the same comments. Each expectation under `tests/review/` is
the edited document's snapshot. The documents and their snapshots go to
`.roc-docx/review/`, where `oracle-schema-written` validates them and the
LibreOffice lane compares LibreOffice's reading with the package's.

The redline cases edit every fixture as the `redline` example edits its
amendment: tracking turned on, one reviewer's changes accepted and another's
rejected, then the first word of the first line of text replaced, text added
to the end of that line with a new paragraph after it, and the last word of
the next line deleted, as tracked changes. The edited document's text must be what the same edits
give made silently, rejecting the new changes must give the text before
them and accepting them the silent edits' text, and the edited document must
write twice to the same bytes and read back with the same changes and
tracking on. Each expectation under `tests/redline/` is the edited
document's snapshot; the documents and snapshots go to `.roc-docx/redline/`,
which `oracle-schema-written` and the LibreOffice lane read as they read the
review cases'.

== Performance ratchets

There are no speed targets. Each fuzz target wraps every public entry point it
tests in a `Fuzz.measure!` region named after it, such as `opc-open` or
`xml-tree-parse`, and asserts ceilings on its allocation count and peak live
bytes: linear ceilings for every generated input and exact ceilings for its
declared examples. An operation that iterates a document also declares a small
and a large example, and when the large one runs it measures the small one
again and fails if it costs more than the linear ratio the target states for
the pair, in allocations, bytes requested and bytes held live. Where a
constant dominates the small example, such as the DEFLATE compressor that
every written document needs, the ratio is stated over that constant: the
large example may cost the small one's plus a stated share for each further
byte, so `Docx.parse` and `Docx.to_bytes` on the largest fixture are bounded
by a one-paragraph document and the fixture's further bytes. That check
holds even when both exact ceilings are raised, so growth beyond linear
cannot be ratcheted in. Sets, dictionaries and lists grow by doubling, so the
bytes an item costs rise and fall as counts cross their capacities; where
that carries a pair's bytes past the count ratio, the target allows a stated
margin beside the per-item range it measured, as `fuzz/comment_anchors` does
for writing comments, small enough that a quadratic step still fails. A list
that starts with fixed room requests up to about twice its final size over
its growth, while a small example's list may fit that room and never grow,
which carries a pair's bytes towards twice the count ratio. Where a cheap
count of the items is at hand, the list is made at that size instead, as
`Docx.revisions` counts the changes before it lists them. A loop that
carries a value exactly as a parameter gave it can copy that value's
collections at every change instead of updating them in place, which the
pair check shows as bytes per item that grow with the document. A loop in
the package whose state is a record holding a list, set, dictionary or
string therefore starts from a record update of the state it is given, such
as `{ ..state, next: state.next }`, and the lint rejects one that starts
from the parameter as it is. To set or revise a ceiling:

[source,sh]
----
roc build --fuzz fuzz/opc_open/main.roc --output=.roc-docx/fuzz/opc_open
.roc-docx/fuzz/opc_open check --report-dir=.roc-docx/fuzz/reports/measure
----

Read `report.json` in the report directory: each example lists its regions
with `allocs`, `reallocs`, `requested_bytes` and `peak_live_bytes`. Set an
exact ceiling to the measured `allocs + reallocs`. A ceiling only moves down:
lower it when a change allocates less, and when a change needs a higher
ceiling, record the cause in the pull request beside the new value.

== Fixtures and oracles

Fixtures under `tests/fixtures/` are documents the package reads in tests.
Only self-authored or generated content is admitted, and every file has an
entry in `tests/fixtures/provenance.json`. The pandoc fixtures are regenerated
from `tests/fixtures/sources/*.md` by `blueprint run fixtures`; the
LibreOffice fixtures are round trips produced by
`python3 -I oracle/make_fixtures.py --libreoffice` and committed with the
version recorded.

The Word fixtures under `tests/fixtures/word/` are Microsoft Word's own
serialization of documents the repository authors: comment threads with
replies and a resolved thread, every kind of tracked change Word keeps, a
table with merged cells, and a report with headers, footers, notes, links,
a bookmark, lists and an image. Word's scripting cannot create most of these,
so `oracle/make_word_fixtures.py` writes each as a seed package with
fictional authors, has Word open and save it, and checks that Word kept every
construct and that no part carries the machine's user or account names. It
needs macOS with Word installed and is run by a maintainer, never by `check`
or CI:

[source,sh]
----
python3 -I oracle/make_word_fixtures.py
----

Word output is not reproducible, so the fixtures are committed with the Word
version in their provenance and `fixtures-check` does not regenerate them.
Word records the signed-in account as the last editor whatever its user name
setting says; the script replaces that one property with the seed's fictional
editor and copies every other archive entry unchanged.

The Google Docs fixture under `tests/fixtures/gdocs/` is Google Docs' own
export of a résumé of placeholder text with comments, written by hand in
Google Docs and downloaded as a Word document. Google Docs stamps the
exporting account's name on comments and revisions and embeds the fonts the
document uses, so `oracle/scrub_gdocs_fixture.py` makes every author
fictional and removes the embedded fonts with their relationships, then
checks that no part names the maintainer, that every relationship resolves
and that LibreOffice converts the result. It is run by a maintainer, never by
`check` or CI, on an export the maintainer made:

[source,sh]
----
python3 -I oracle/scrub_gdocs_fixture.py ~/Downloads/Resume.docx
----

The export is what makes the fixture worth having: it declares an extension
namespace it does not mark ignorable, writes decimal values where the schema
wants whole numbers and leaves out a required attribute, so the schema oracle
reports its parts as accepted deviations while the package's pass-through of
it must validate.

The oracle adapters under `oracle/` are deliberately Python: an independent
implementation cannot share the package's mistakes. When an oracle disagrees
with the package, find the cause. A finding that is known to be wrong or out
of the package's control is recorded in `conformance/accepted-deviations.json`
with its oracle, rule, document, cause and an upstream reference.

== Compare readers with snapshots

A snapshot is what one reader understood of a document, reduced to facts that
another reader can be checked against. `oracle/snapshot_schema.json` defines
it as `roc-docx-snapshot/1`. Every reader writes every field, using the empty
value for what it does not know, and lists in `keys` the fields it is
authoritative for. Two snapshots are compared only on the keys both list.

[cols="1,3",options="header"]
|===
| Field | What it holds

| `blocks`
| The body in reading order. Each block has a `kind` (`paragraph`, `heading`,
`list_item` or `table`), a `level` (a heading's outline level or a list
item's depth, from 1), a `list` kind (`bullet` or `number`), its current
`text`, its `runs`, and for a table its `rows` as a grid of cell texts. A
paragraph with no text that anchors no note, comment or revision is not a
block.

| `runs`
| A block's text split where direct formatting changes, each with `bold`,
`italic`, `underline`, `strike`, `superscript`, `subscript` and a hyperlink
target in `link`. What paragraph and character styles contribute is not run
formatting.

| `notes`
| Footnotes and endnotes in reference order, with `kind` and `text`.

| `comments`
| Comments in anchor order, with `author`, `date`, `text`, the `anchor` text
they cover, `resolved`, and `thread`: the index of the comment that starts
the thread, which is a comment's own index unless it is a reply.

| `revisions`
| Tracked changes in body order, with `kind` (`insertion`, `deletion` or
`format`), `author`, `date` and the `text` they change.

| `sections`
| Page width, height, orientation and margins in twips, and the text of the
header and footer on the section's odd, even and first pages: the even
pages' differ only where the document has different odd and even pages, and
the first page's only where the section has a title page.

| `properties`
| The core properties: title, subject, creator, keywords, description, last
modified by, created and modified.
|===

The current text of a paragraph includes inserted and moved-in text and
leaves out deleted and moved-away text, note references and comment
content. A paragraph whose mark is deleted is one block with the paragraph
after it, unless a table comes between them. Paragraphs inside notes,
comments, cells and multi-paragraph anchors are joined with a line feed.

The comparison normalizes before it compares: line endings become line
feeds and then text compares exactly; dates compare as instants, a date
without a zone being UTC; runs are projected onto the run keys both sides
declare and neighbours that become equal are joined; order is significant
everywhere.

The package is compared with the oracles the same way. `Snapshot.json`
writes its reading of a document as a snapshot that declares only the keys
it is authoritative for so far: every block, run, note, section and property
key, and the comments' `author`, `date`, `text`, `anchor`, `thread` and
`resolved`; the `snapshots` cases
of `tests/main.roc` write one for every fixture under `.roc-docx/snapshots/`
and check it against `tests/snapshots/`; and `oracle/snapshot_package.py`, the
`package` adapter, only copies those files, so a lane compares exactly what
the package wrote. Run the cases before a lane that includes `package`.

Two oracle adapters produce snapshots, each in its own file and sharing
nothing with the package or each other. `oracle/snapshot_pandoc.py` reduces
pandoc's JSON reading of a document; it is not authoritative for note kinds,
comment threads or resolution, sections or properties. It restores the title,
subtitle, author, date and abstract paragraphs that pandoc moves into
metadata. `oracle/snapshot_libreoffice.py` reduces LibreOffice's Flat ODT
conversion, following the parent each reply names to the comment that
starts its thread; it is authoritative for every key except the properties
other than title, creator, created and modified, whose mapping is not yet
verified. Each adapter's docstring lists the
rules it applies and why.

Run one adapter on a document, or compare two snapshots, directly:

[source,sh]
----
python3 -I oracle/snapshot_pandoc.py tests/fixtures/pandoc/review.docx > pandoc.json
python3 -I oracle/snapshot_libreoffice.py tests/fixtures/pandoc/review.docx > libreoffice.json
python3 -I oracle/compare_snapshots.py pandoc.json libreoffice.json
----

A disagreement is a finding to explain, not to silence. Most are adapter
bugs, fixed in the adapter with the reason in the pull request. A reader that
cannot see a key stops declaring it, with the reason in its docstring. What
is left is a deviation of one oracle, recorded with its `key` and a pattern
for the comparison's message in `conformance/accepted-deviations.json`; the
lane prints it as `ACCEPTED`, apart from agreements.

== Keep the manual current

This manual under `docs/` is the documentation for application authors and
contributors. Change it in the same pull request as the behaviour it
describes. Each chapter answers one reader's question, in the form that fits:
a tutorial, a how-to, a reference or an explanation. Keep it release-neutral;
exact versions and pins belong in release notes. The chapters follow the
https://lukewilliamboswell.github.io/roc-automation/documentation.html[roc-automation documentation conventions]
and are rendered by its shared renderer with `blueprint run docs`, which
treats a warning as an error:

[source,sh]
----
blueprint run docs     # the site, the PDF and the API reference, under .docs-out/
blueprint run manual   # every Roc listing of the manual, compiled and run
----

Every Roc listing in a chapter is included from a program that `check`
compiles and runs, never written out in the chapter, so the manual cannot
show code that does not compile. A short listing is a region of
`tests/manual.roc` between `# tag::name[]` and `# end::name[]` comments,
inside a function that runs it on a document of the repository; the chapter
includes it with `include::../tests/manual.roc[tag=name,indent=0]`. A whole
program is an example, included as it is. The lint rejects a listing that is
neither, or that names a region the program does not have; release notes
are exempt, because the release fills in their package URL.

The API reference is generated by `roc docs` from the doc comments of the
modules `package/main.roc` exposes, and published beside the manual under
`api/`. A module's doc comment and each of its public declarations' are
written for application authors, as the manual is.

The https://lukewilliamboswell.github.io/roc-docx/[documentation site] leads
with the latest release, because that is what its readers use: its front
page gives the release's package URL, its examples archive and its API
reference, restored from the release's documentation archive, and offers a
newer release candidate beside it. The default branch's manual, its PDF and
its API reference are published under `unreleased/`. The `docs` workflow
assembles the site from the working tree and the release assets, so nothing
rendered is committed. It builds the site on every pull request, as the
`docs` check, whose `github-pages` artifact is the site to preview, and
deploys it from the default branch and again after every release, because a
release changes what the site leads with.

== Pull requests

One change per pull request, small enough for one reviewer. The description
says what changed, what was run and what it reported, and names anything
discovered and deliberately left for later. Baselines, snapshots and fixture
regenerations are reviewed as diffs; CI never updates them.
