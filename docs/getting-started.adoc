= Read the parts of a document

This chapter opens a `.docx` and lists the parts inside it. It needs a Roc
nightly on your `PATH` as `roc`. Until the first release, an application
depends on the package by relative path from a checkout of the repository.

== What a document is made of

A `.docx` is a ZIP archive of XML parts: the body in one part, styles,
numbering, comments, footnotes, headers and footers in others, with images as
binary parts. `[Content_Types].xml` labels every part, and relationship parts
link a source part to its targets, so the body is found by following the
package's `officeDocument` relationship rather than by its file name.

`Opc.open` reads the archive within resource limits and labels every part
with its content type and size. It keeps the archive as it is and inflates a
part only when you ask for it with `Opc.part_bytes`, so opening a document
costs memory in proportion to its archive rather than to its content.
`Opc.main_document` follows the relationship to the body, and
`Opc.relationships` lists what a part links to. Part names compare without
regard to ASCII case, as the conventions require, so `/word/document.xml`
and `/Word/Document.xml` name the same part.

== The example

The repository's `examples/inspect` does exactly that for the document beside
it, or for a path you pass:

[source,roc]
----
include::../examples/inspect/main.roc[]
----

Run it from its directory:

[source,sh]
----
cd examples/inspect && roc main.roc
----

The output names each part with its content type and size, then the
relationships of the main document: its styles, numbering, settings,
footnotes and comments parts.

== Limits

Documents are untrusted input. `Opc.open` takes a props record of limits
beside the bytes; `{}` keeps every default, and naming one field lowers it:

[source,roc]
----
Opc.open(bytes, { max_entries: 64 })
----

The defaults allow 4096 entries, 64 MiB per part and 256 MiB in total. A
document over a limit fails with the limit's own error, such as
`TooManyEntries(count)`, `PartTooLarge({ name, bytes })` or
`PackageTooLarge(bytes)`. The limits are checked against the sizes the
archive declares, before anything is decompressed, so a small archive that
would inflate to gigabytes is refused without inflating it. `Opc.open` checks,
in order:

. the archive's own size against the total limit;
. the archive's directory of entries, which is read without decompressing
  anything;
. the number of entries;
. each entry's declared size against the part limit, and their running total
  against the total limit;
. that no two part names differ only in case;
. `[Content_Types].xml`, which is decompressed and read;
. a content type for every part, and each relationship part, decompressed.

A part is decompressed into a buffer of the size its entry declares and no
further, so an archive that lies about a size fails with
`PartSizeMismatch({ name, declared })` at the declared size rather than
running on. The other errors say what is wrong with the archive, such as
`DuplicatePart(name)` for two parts with the same name, or with
`[Content_Types].xml`; none of them is a crash. `Opc.part_bytes` reports the
same kinds of damage for the part it decompresses.
